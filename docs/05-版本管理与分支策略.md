# 05 · 版本管理与分支策略（Versioning & Branching）

> 对应 Skill：`wolf-release-versioning`。基线以 [`_conventions.md`](./_conventions.md) 第 3 节为唯一事实源；总纲见 [`00-master-plan.md`](./00-master-plan.md) 第 8 节。本文只落地命令与配置。

---

## 1. 分支模型：Trunk-based + 短分支

```
main ──────────────────────────────────────────►（永远可发布，禁止直接 push）
  │           │             │
  │ feat/*    │ fix/*       │ hotfix/*           （≤ 3 天，关联需求号）
  │ ≤3天      │ ≤3天        │ 随时，24h 回灌
  └──── PR ───┴──── PR ─────┴─── PR（过全部门禁后 squash 合并）
release/x.y 仅用于 LTS 维护，不参与日常开发
```

**规则（与 3 节一致）**：

1. 一切改动经 PR 进入 `main`；PR 必须过全部门禁（lint/test/build/契约/安全），见 [`06-CICD与部署.md`](./06-CICD与部署.md)。
2. 分支生命周期 ≤ 3 天，超期自动提醒（`scripts/pr-stale-check.sh` 或 GitHub Actions `stale`）。
3. 合并策略统一 **squash**，保持 `main` 历史一条线、可 `revert`。
4. `hotfix/*` 从 `main` 切出，修复后**同时**打 tag 发补丁版 + 合并回 `main`，24h 内必须回灌。

**分支生命周期图（带门禁）**：

```
feat/PE-123-quotation-engine
   ├─ 0h   创建（git switch -c）
   ├─ 0-72h 开发 + 本地 TDD（见 04 号文档）
   ├─ PR    全部门禁 green
   ├─ review 1+ 通过
   └─ squash merge → main → 自动发 CHANGELOG + 制品
```

## 2. Conventional Commits 规范

格式：`<type>[optional scope]: <subject>`，subject 用祈使句、小写开头、不加句号；正文可补 `BREAKING CHANGE:` 与关联需求号 `PE-xxx`。

| type | 用途 |
| --- | --- |
| `feat` | 新功能（触发 minor） |
| `fix` | 缺陷修复（触发 patch） |
| `docs` / `refactor` / `perf` / `test` / `build` / `ci` / `chore` / `revert` | 不触发版本（或按 scope 判定） |
| `feat!` / `fix!`（或正文 `BREAKING CHANGE:`） | 触发 major |

**正例**：

```
feat(quotation): add AI price suggestion endpoint
fix(order): correct urgent-order priority sorting
feat!(iam): drop legacy session cookie auth

BREAKING CHANGE: 旧版 cookie 登录不再支持，需迁移到 JWT
```

**反例（禁止）**：

```
改了报价逻辑                      # 无 type，中文裸写
feat: 增加报价接口                # subject 未用英文祈使句
Update some files                 # 语义不清，无法自动归类
fix(#1234)                        # 编号应放正文，不在标题
WIP / temp / 111                  # 无意义占位
```

## 3. Changesets：按端独立 SemVer

> 语义版本：`erp-console@1.4.0`、`backend@1.4.2`、`customer-mini@0.9.1` 各自演进，互不牵连。Changesets 依据 commit 与 `.changeset/*.md` 汇总，自动 bump 并生成 CHANGELOG。

### 3.1 配置（`.changeset/config.json`）

```json
{
  "$schema": "https://unpkg.com/@changesets/config@3.0.0/schema.json",
  "changelog": "@changesets/cli/changelog",
  "commit": false,
  "fixed": [],
  "linked": [["@perp/portal-core", "@perp/api-client", "@perp/domain-types"]],
  "access": "restricted",
  "baseBranch": "main",
  "updateInternalDependencies": "patch",
  "privatePackages": { "version": true, "tag": true }
}
```

- `linked`：共享内核 `portal-core` 与生成产物 `api-client/domain-types` 联升，避免口径漂移。
- `backend`（`services/erp-server`）与 `ai-service` 作为独立 package 纳入同一 Changesets 管理。

### 3.2 打变更集

```bash
pnpm changeset            # 交互式：选包 → 选 bump(major/minor/patch) → 写描述
# 产出 .changeset/xxx.md，随 PR 一起提交
```

变更集片段示例（`.changeset/quick-foxes-jump.md`）：

```md
---
"@perp/erp-console": minor
"@perp/backend": patch
---

新增报价单批量导出；修复加急单排序。
```

### 3.3 发布命令

```bash
# 1) 合并到 main 后，自动 PR（Release Pull Request）由 changesets/action 创建
# 2) 合并 Release PR 触发发布：
pnpm changeset version          # 依据 .changeset 汇总 bump 版本 + 生成 CHANGELOG
pnpm changeset publish          # 发 npm/GitHub Packages
# 3) 打注解标签（与镜像 tag、Helm chart version 一一对应）
git tag -a "erp-console@1.5.0" -m "erp-console@1.5.0"
git tag -a "backend@1.4.3"      -m "backend@1.4.3"
git push origin --tags
```

## 4. CHANGELOG 自动生成与标签规范

- CHANGELOG：由 Changesets 按 `feat/fix/BREAKING` 自动汇总，按包生成 `<pkg>/CHANGELOG.md`。
- 标签：**注解标签** `<app>@<version>`（如 `erp-console@1.5.0`），镜像 tag、Helm `image.tag`、`build-info.json` 三者一致。
- 校验脚本：`scripts/verify-tags.sh` 检查「git tag ↔ 镜像 tag ↔ chart version」三一致，不一致阻止部署。

## 5. 发布节奏

| 事项 | 约定（3 节） |
| --- | --- |
| 迭代 | 双周 Sprint |
| 发布窗口 | 每周三（常规）；`hotfix` 随时 |
| hotfix | 24h 内必须回灌 `main`（CI 校验 `hotfix` 分支 age < 24h） |
| LTS | `release/x.y` 仅做维护，不打新功能 |

## 6. 数据库 Expand/Contract 迁移与回滚

> 目标：镜像可回滚（切回上一 tag），而**数据库永不回滚**。所有 schema 变更走"向前兼容"三步，回滚不依赖 DB 回退。

```
Expand（新增，兼容旧代码） ──► Contract（删除，须等旧代码全部下线）
```

| 步骤 | 动作 | 说明 |
| --- | --- | --- |
| 1 Expand | 新增列/表（可空、带默认值） | 旧、新代码都兼容 |
| 2 双写/回填 | 数据回填 + 双读 | 灰度期间数据一致 |
| 3 Contract | 删除旧列/表 | 待旧版本镜像 100% 下线后再执行，独立于应用发布 |

```sql
-- 例：订单表新增"交期风险分"列（Expand）
ALTER TABLE sales_orders ADD COLUMN delivery_risk_score numeric NULL;
-- Contract（下一版本，旧代码已全部下线后）
ALTER TABLE sales_orders DROP COLUMN delivery_risk_score;
```

回滚 = 镜像切回上一 tag；DB 不回滚，仅保持新 schema 向前兼容。

## 7. 制品可追溯：build-info.json

每次构建写入 `build-info.json`，随制品（镜像 label + OCI 注解）发布：

```json
{
  "app": "erp-console",
  "version": "1.5.0",
  "commit_sha": "9fceb02...",
  "build_number": "github.run_number",
  "build_time": "2025-06-18T09:00:00Z",
  "sbom": "sbom.spdx.json",
  "signature": "cosign 签名摘要",
  "source_ref": "https://github.com/<org>/p-erp/tree/9fceb02"
}
```

验证：`cosign verify --key cosign.pub <image>:<tag>`；`build-info.json` 内 SHA 必须等于触发构建的 commit。

## 8. release-please 工作流

```yaml
# .github/workflows/release.yml（Changesets 也可换成 release-please，二选一）
name: release
on:
  push:
    branches: [main]
jobs:
  release:
    runs-on: [self-hosted, linux]
    steps:
      - uses: googleapis/release-please-action@v4
        with:
          release-type: node            # 或 java
          package-name: p-erp
      - run: pnpm build && pnpm publish
        if: ${{ steps.release.outputs.release_created }}
```

> 说明：本仓库前端用 Changesets（§3）为默认；Java 后端可用 release-please。两者都满足「按端独立 SemVer + 自动 CHANGELOG + 注解标签」的 3 节要求，团队二选一后写死即可。

## 9. 回滚步骤（一键）

```bash
# 回滚 = 切回上一镜像 tag（镜像不可变），DB 不回滚
kubectl set image deployment/erp-console erp-console=<registry>/erp-console:1.4.0
# 或 Compose 阶段：
docker compose -f docker-compose.prod.yml up -d --no-deps erp-console \
  --scale erp-console=1 --remove-orphans   # 切回旧 tag 配置
```

完整回滚 SOP 与蓝绿切换见 [`06-CICD与部署.md`](./06-CICD与部署.md) §7。

## 10. 验收清单

- [ ] 分支模型为 Trunk-based + 短分支，`main` 禁止直接 push，`hotfix` 24h 回灌有 CI 校验。
- [ ] commit message 遵循 Conventional Commits，正反例已列入文档。
- [ ] Changesets 配置含 `linked`（portal-core/api-client/domain-types），按端独立 SemVer。
- [ ] 标签为注解标签 `<app>@<version>`，与镜像 tag、Helm chart version 一致。
- [ ] 发布节奏为双周迭代 + 每周三窗口，hotfix 随时。
- [ ] 数据库迁移采用 Expand/Contract，回滚不依赖 DB 回退。
- [ ] `build-info.json` 含 commit SHA + 构建号 + SBOM + 签名，可用 `cosign` 验证。
- [ ] release-please / Changesets 工作流可跑通，CHANGELOG 自动生成。
