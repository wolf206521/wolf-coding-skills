# 10 迭代进化与度量

> 代号 **P-ERP** 的度量与持续进化专项。技术栈、门禁阈值以 [`_conventions.md`](./_conventions.md) 第 2.4/2.5 节为唯一事实源；四维度目标见 [`00-master-plan.md`](./00-master-plan.md) 第 11 节。版本管理见 [`05-版本管理与分支策略.md`](./05-版本管理与分支策略.md)，CI/CD 见 [`06-CICD与部署.md`](./06-CICD与部署.md)，私有化/安全见 [`07-自建与私有化部署.md`](./07-自建与私有化部署.md)，AI 指标口径见 [`08-AI能力与生成型特性.md`](./08-AI能力与生成型特性.md)，路线图见 [`11-路线图与里程碑.md`](./11-路线图与里程碑.md)。

> 原则：**先度量，再决策**。所有「拆不拆微服务」「还不还技术债」「AI 上不上线」都用指标触发，不靠感觉。

---

## 1. 度量四维度

| 维度 | 关注什么 | 关键指标 | 反模式（要预警） |
| --- | --- | --- | --- |
| **交付（DORA）** | 快不快、稳不稳 | Lead Time、部署频率、变更失败率、MTTR | Lead Time 上升、失败率 > 阈值 |
| **质量** | 代码/缺陷/安全 | 缺陷密度、覆盖率、漏洞数 | Blocker/Critical > 0 |
| **业务** | 是否真创造价值 | 报价命中率、订单周期、设备 OEE | 订单周期拉长、OEE 下滑 |
| **AI** | AI 是否可信可用 | 误差率、幻觉率、采纳率 | 误差 > 3%、幻觉 > 2% |

## 2. 度量指标体系表

> 「口径」= 精确计算公式；「采集」= 工具；「目标」= 双周回顾要盯的基线；「看板位置」= Grafana 面板路径。

| 指标 | 口径 | 采集方式 | 目标值 | 看板位置 |
| --- | --- | --- | --- | --- |
| Lead Time | 首次 commit → 生产部署的中位耗时 | CI 流水线元数据 + 部署事件 | ≤ 2 天（中位数） | DORA / Delivery |
| 部署频率 | 生产发布次数 / 周 | Argo CD / 部署事件流 | ≥ 3 次/周（团队） | DORA / Delivery |
| 变更失败率 | 导致回滚/热修的部署数 / 总部署数 | 回滚事件 + hotfix 分支 | ≤ 5% | DORA / Stability |
| MTTR | 故障发现 → 恢复的中位耗时 | Pager/告警 + 恢复时间戳 | ≤ 30 分钟 | DORA / Stability |
| 缺陷密度 | 未关闭缺陷数 / 千行代码（KLOC） | 缺陷工单 + 代码行数 | ≤ 1 个/KLOC | Quality / Defects |
| 行覆盖率 | 单测覆盖行 / 总行 | SonarQube | ≥ 70%（核心域 ≥ 85%） | Quality / Coverage |
| 高危漏洞数 | Trivy/Semgrep/ZAP 高危合计 | 扫描报告聚合 | = 0 | Security / Vulns |
| 报价命中率 | 采纳报价单数 / 生成报价单数 | 报价单状态流转 | ≥ 60%（与 AI 采纳率联动） | Business / Quotation |
| 订单周期 | 接单 → 发运的日历天中位数 | 订单/发运时间戳 | 按产品线设基线 | Business / Order |
| 设备 OEE | 可用率 × 性能 × 良率 | MES/设备采集 | ≥ 75% | Business / OEE |
| AI 误差率 | \|预测价-成交价\|/成交价 | 黄金集 + Langfuse | ≤ 3% | AI / Accuracy |
| AI 幻觉率 | 幻觉输出 / 总输出 | Ragas + 人工抽检 | ≤ 2% | AI / Quality |
| AI 采纳率 | 用户采用 AI 输出比例 | Langfuse 👍/落单埋点 | ≥ 60% | AI / Adoption |
| 技术债比 | 技术债工时 / 迭代总工时 | 技术债看板工时 | ≤ 20% | TechDebt / Ratio |
| 准交率（OTIF） | 准时交付订单数 / 总订单数 | 订单 + 发运时间戳 | ≥ 95% | Business / OTIF |
| SLO 达成率 | 满足 SLO 的请求 / 总请求 | Prometheus SLO | ≥ 99.9% | SRE / SLO |
| 错误预算剩余 | 1 − (超 SLO 时间 / 窗口) | burn rate 告警 | > 0（不烧穿） | SRE / ErrorBudget |
| 客服解决率 | AI 独立解决咨询数 / 总咨询数 | 客服工单 + AI 埋点 | ≥ 40%（一期） | AI / CSAT |

## 3. 双周回顾机制

### 3.1 会议模板（每 Sprint 末，≤ 60 分钟）

| 环节 | 时长 | 输入 | 产出 |
| --- | --- | --- | --- |
| 0 数据先行 | 10min | §2 看板截图（四维度） | 哪些指标绿/黄/红 |
| 1 红指标归因 | 15min | 红/黄指标 + 事件流水 | 每个红指标 1 条根因假设 |
| 2 改进项投票 | 10min | 归因结果 | 本迭代 ≤ 3 条可执行改进项（含负责人/截止） |
| 3 技术债评估 | 10min | 技术债看板（§5） | 是否触发偿还、还哪笔 |
| 4 拆分/演进决策 | 10min | 拆分触发阈值（§6） | 是否启动拆分 ADR |
| 5 AI 评测复盘 | 5min | AI 门禁结果 + 人工抽检 | 是否调整黄金集/prompt 版本 |

### 3.2 红黄绿规则

- **绿**：达到目标值。**黄**：连续 1 次迭代未达标 → 进入观察，记录假设。
- **红**：连续 2 次迭代未达标 或 触发 §2 反模式 → 强制进入「归因 + 改进项」，且改进项下迭代必须关闭。

## 4. 技术债看板与偿还策略

### 4.1 技术债分级标准

| 级别 | 定义 | 举例 | 处置时限 |
| --- | --- | --- | --- |
| **L0 阻断** | 阻塞交付/危及生产 | 高危漏洞、数据丢失、无法回滚 | 立即处理（hotfix） |
| **L1 严重** | 1 个迭代内会扩散 | 模块跨边界依赖（ArchUnit 违规）、契约漂移 | 下迭代必还 |
| **L2 一般** | 影响速度但不阻断 | 重复代码、过期注释、低覆盖模块 | 排入偿还池，按 §4.2 还 |
| **L3 可接受** | 有意接受的取舍 | 预留但未用的接口、一期妥协方案 | 记录 + 定期复审 |

### 4.2 偿还策略

- **债务登记**：技术债在 Git 里以 `techdebt:` 提交 + 看板条目，标 `L0-L3` + 影响模块 + 偿还成本。
- **偿还预算**：每迭代固定 20% 工时额度还债；超预算则触发「还债 vs 新功能」优先级裁决（产品 + 架构共同决定）。
- **L1/L2 优先规则**：按「扩散速度 × 被踩频率」排序，先还扩散快、天天被踩的债。

## 5. 数据驱动「模块化单体 → 微服务」拆分时机

> 起点是模块化单体（[`_conventions.md`](./_conventions.md) 第 2.1 节 Spring Modulith），**拆分是被指标逼出来的结果**，不是起点。满足任一触发才启动 ADR 评估。

| 触发阈值 | 含义 | 采集来源 |
| --- | --- | --- |
| 单模块部署频率显著高于其余 | 某模块一周发布 > 5 次，其余 < 1 次 | 部署事件 |
| 性能热点单点 | 某模块 P95 持续超阈值且无法水平扩展 | APM/Tempo |
| 团队边界冲突 | 多团队改同一模块，PR 冲突率 > 30% | Git 元数据 |
| 数据规模分层 | 单表 > 千万行且读写分离到极限 | 数据库监控 |
| 独立 SLA/合规 | 某模块需独立扩容或隔离（如 AI 服务已独立） | 架构评审 |

- **评估**：满足阈值 → 写 ADR（背景/选项/决策/后果/回滚条件）→ 与 [`01-架构设计.md`](./01-架构设计.md) 对齐 → 再拆。禁止「为了微服务而微服务」。

## 6. A/B 与灰度度量

- **A/B**：针对 AI 能力（报价话术、排产建议、客服话术）与前端体验，用 `feature flag`（如 `OpenFeature`/自研）分流，对照组/实验组各 50%，观察 **采纳率/报价命中率/客服解决率**，统计显著（p < 0.05，样本量 ≥ 200）才全量。
- **灰度度量**：新版本按 5% → 20% → 50% → 100% 放量，每档观察失败率、错误率、P95；任一口径恶化即回滚镜像（不可变镜像 + 前向兼容迁移，见 [`_conventions.md`](./_conventions.md) 第 3 节）。
- **通用护栏**：A/B/灰度期间必须同时看「业务指标 + 技术指标」，只看业务不看错误率是典型反模式。

## 7. 持续进化的治理组织

| 角色 | 度量责任 | 频率 |
| --- | --- | --- |
| **架构负责人** | 技术债看板、拆分阈值触发、ADR 维护 | 每迭代 |
| **Tech Lead（后端/前端/AI）** | 各自维度的质量/AI 指标达标、改进项落地 | 每迭代 |
| **SRE/运维** | DORA 四指标、SLO、故障复盘 | 每迭代 + 故障即时 |
| **产品负责人** | 业务指标（报价命中率/订单周期/OEE）口径与目标 | 每迭代 |
| **QA 负责人** | 缺陷密度、覆盖率、AI 黄金集维护 | 每迭代 |
| **度量看门人（可兼任）** | 汇总四维度看板、主持双周回顾、追踪改进项闭环 | 每迭代 |

- **铁律**：每个指标必须有唯一责任人（DRI），红指标必须有改进项闭环，否则回顾会议不算完成。

## 8. 度量数据采集链路与看板实现

- **统一采集**：应用埋点（结构化 JSON 日志 + traceId）→ OpenTelemetry Collector → Prometheus（指标）/ Loki（日志）/ Tempo（链路），对应 [`_conventions.md`](./_conventions.md) 第 2.5 节。
- **DORA 四指标**：从 CI 事件 + Argo CD 部署事件 + 告警恢复时间戳聚合，写 Grafana 自定义面板（§2 看板位置即面板路径）。
- **业务指标**：报价命中率/订单周期/OEE 来自业务库（`quotations`/`sales_orders`/设备采集表，见 [`09-领域模型与业务流程.md`](./09-领域模型与业务流程.md) 第 6 节），由 Spring Batch 定时聚合到指标表。
- **AI 指标**：Langfuse 事件 + 黄金集评测结果写入 `ai_traces`，误差率/幻觉率/采纳率自动回填（见 [`08-AI能力与生成型特性.md`](./08-AI能力与生成型特性.md)）。
- **看板分层**：一层「高管看板」（业务 + DORA 摘要）、一层「工程看板」（质量/技术债/拆分）、一层「AI 看板」（误差/幻觉/采纳）。三层共用一个 Prometheus 数据源，口径唯一。

## 9. 改进项闭环与示例

| 字段 | 示例 |
| --- | --- |
| 红指标 | AI 报价误差率连续 2 迭代 3.8%（目标 ≤ 3%） |
| 根因假设 | 黄金集样本过旧，未覆盖 2024 新纸张价 |
| 改进项 | 更新黄金集 + 报价规则纸张价基线 + 重跑评测 |
| 负责人/截止 | AI 工程师 / 本迭代末 |
| 关闭条件 | 误差率 ≤ 3% 且黄金集样本 ≥ 320 条 |

- **闭环追踪**：改进项进看板，未关闭自动流转到下一迭代回顾的「红指标归因」环节，连续 3 迭代未关闭升级给架构负责人。
