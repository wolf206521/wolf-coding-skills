# 02 多端与门户拆分

> 本文定义「四端 + 小程序」的拆分边界、权限域、数据可见性、端选择矩阵与部署规划。
> 门户拆分结论以 [`_conventions.md`](./_conventions.md) 第 1 节为唯一事实源；总体架构见 [`01-架构设计.md`](./01-架构设计.md)；开发流程见 [`03-开发流程与工程规范.md`](./03-开发流程与工程规范.md)。

---

## 1. 结论：一个 Monorepo + 多个独立应用 + portal-core 共享内核

### 1.1 为什么"分开，但不分家"

| 维度 | 必须分开 | 不能分家 |
| --- | --- | --- |
| 法律/商务 | 客户、供应商、外协、企业是不同法律主体 | 领域对象重合 ≥ 70% |
| 权限/数据 | 客户绝不能看到供应商价格、成本 | 单据结构一致 |
| 发版节奏 | 各自独立上线、独立回滚 | UI 骨架重合 ≥ 60% |
| SLA | 协同端可降级，ERP 后台优先保 | 口径必须统一 |

**落地**：`packages/portal-core` 提供 `认证/权限/请求层/领域类型/业务规则/UI 骨架/单据组件`；各 app 只写自己独有的路由与视图。分应用是为了「隔离与独立发版」，共享内核是为了「避免三倍缺陷与口径漂移」。

### 1.2 应用清单（与 `_conventions.md` 第 1.1 节一致）

| 应用 | 目录 | 使用者 | 端 | 部署单元 |
| --- | --- | --- | --- | --- |
| ERP 后台 | `apps/erp-console` | 企业内部 | Web（PC） | 独立 |
| 客户侧 | `apps/customer-portal` | 客户 | Web + H5 | 独立 |
| 客户侧小程序 | `apps/customer-mini` | 客户 | 微信小程序 | 独立 |
| 供应商侧 | `apps/supplier-portal` | 供应商 | Web + H5 | 独立 |
| 外协侧 | `apps/outsourcing-portal` | 外协厂 | Web + H5 | 独立 |
| 共享内核 | `packages/portal-core` | 协同三端 | — | 库（不部署） |

> 注：`_conventions.md` 中的「三个独立应用」指协同三端（客户/供应商/外协）——它们共享 `portal-core`；ERP 后台与客户小程序作为另两个独立构建单元，总计 5 个可部署产物。

## 2. 四端权限域

| 端 | 认证方式 | 角色 | 权限域 |
| --- | --- | --- | --- |
| ERP 后台 | 账密 + 短信/TOTP 二次验证 | 业务员/工艺/生产/仓管/财务/管理员 | 全量内部功能 + 管理权限点 |
| 客户侧 | 手机验证码 + 微信授权（小程序） | 客户联系人/客户管理员 | 仅自己单据（下单/进度/验货/对账） |
| 供应商侧 | 手机验证码（H5 企业微信） | 供应商联系人 | 仅自己采购单/送货/对账 |
| 外协侧 | 手机验证码（H5 企业微信） | 外协联系人 | 仅自己外协单/报工/质检反馈 |

Token 内嵌 `partner_type/partner_id`（`_conventions.md` 第 5 节），网关校验；`partner_type ∈ {customer, supplier, outsourcing}`。

## 4. 数据可见性矩阵表（谁能看到什么字段）

> ✅ 可见　◐ 仅自己的值　❌ 永久脱敏（后端 DTO 裁剪，不依赖前端隐藏）

| 字段 | ERP 后台 | 客户侧 | 供应商侧 | 外协侧 |
| --- | --- | --- | --- | --- |
| `sales_orders` 订单号/数量/交期/状态 | ✅ | ◐ | — | — |
| `sales_orders.unit_price`（销售单价） | ✅ | ◐ 自己的 | ❌ | ❌ |
| `sales_orders.cost`（成本） | ✅ | ❌ | ❌ | ❌ |
| `supplier_price`（供货价） | ✅ | ❌ | ◐ 自己的 | ❌ |
| `outsource_price`（外协加工价） | ✅ | ❌ | ❌ | ◐ 自己的 |
| `paper_stock` 库存量/成本 | ✅ | ❌ | ❌ | ❌ |
| 其他客户/供应商信息 | ✅ | ❌ | ❌ | ❌ |
| 工艺/拼版参数 | ✅ | ◐ 只读结果 | — | ◐ 加工要求 |
| 质检/退单原因 | ✅ | ◐ 自己的 | — | ◐ 自己的 |

裁剪实现（后端 Assembler 按 `partner_type` 分组，响应对象只放允许字段）：

```java
// services/erp-server/.../interfaces/assembler/SalesOrderAssembler.java
public SalesOrderView toView(SalesOrder o, PartnerContext ctx) {
    SalesOrderView v = SalesOrderView.basic(o);          // 订单号/数量/交期/状态
    if (ctx.isInternal())  { v.setUnitPrice(o.unitPrice()); v.setCost(o.cost()); }
    if (ctx.isCustomer() && ctx.owns(o.partnerId())) v.setUnitPrice(o.unitPrice());
    // supplier/outsourcing 不注入任何价格字段；字段级防线见 01-架构设计 §7
    return v;
}
```

| 场景 | Web | H5 | 微信小程序 | 决策 |
| --- | --- | --- | --- | --- |
| ERP 后台（PC 办公） | ✅ 首选 | — | — | 仅 Web |
| 客户下单/查进度/验货/对账（移动） | ◐ | ✅ | ✅ | Web+H5+小程序 |

| 外协报工/拍照（车间移动） | — | ✅（企业微信内） | — | 仅 H5 |

## 6. 为什么小程序只做客户侧

1. **客户侧高频移动**：下单/查进度/验货确认/对账，移动诉求真实，ROI 高。
2. **供应商/外协低频 + 需传文件**：接单对账频次低，报工需上传文件/工序照片，H5（企业微信内打开）已足够，做小程序 ROI 低。
3. **口径一致**：小程序与客户 Web 用同一 `portal-core` + 同一 OpenAPI 生成的 client，不产生第二套业务口径。
4. **审核与成本**：小程序审核/备案/年审成本，多端摊薄不划算。

## 7. portal-core 包的内容边界

### 7.1 模块划分（`packages/portal-core/src/`）

```
portal-core/src/
├── auth/            # JWT 解析、token 刷新、partner_type/partner_id 提取
├── permission/      # 权限点判断、菜单/按钮级鉴权（纯函数 + hook）
├── http/            # 请求封装、错误归一、401 跳登录、重试策略
├── domain/          # 领域类型与枚举（由后端 schema 生成，禁止手写）
├── rules/           # 纯函数业务规则（报价试算、损耗计算）——复用 packages/business-rules
├── ui/
│   ├── shell/       # 布局骨架、导航、主题、多端响应式
│   ├── order/       # 订单列表/详情/状态流转组件
│   ├── statement/   # 对账单组件
│   └── upload/      # 分片上传/断点续传组件（MinIO 直传）
└── mode.ts          # PORTAL_MODE 编译期开关
```

### 7.2 边界（什么放进来 / 什么不放）

| 放进来 | 不放进来 |
| --- | --- |
| 协同三端共用的认证/权限/请求/领域类型/单据组件/UI 骨架 | 各端独有路由、页面、菜单、品牌文案 |
| 纯函数业务规则（可前端复用） | 依赖后端状态的服务端逻辑 |
| 由 OpenAPI 生成的 client 与类型 | 任何手写的接口类型（违反契约优先） |

## 8. PORTAL_MODE 降级开关

一期资源紧张时，允许用**同一 app 构建出 supplier/outsourcing 两侧产物**，二期再物理拆分目录。开关定义在 `packages/portal-core/src/mode.ts`：

```ts
export type PortalMode = 'customer' | 'supplier' | 'outsourcing';
export const PORTAL_MODE: PortalMode =
  (import.meta.env.VITE_PORTAL_MODE as PortalMode) ?? 'customer';

export const isSupplier = PORTAL_MODE === 'supplier';
export const isOutsourcing = PORTAL_MODE === 'outsourcing';
```

使用方式（各 app 的 `vite.config.ts` / `.env`）：

```bash
# 一期：同一仓库同一 app，按 mode 构建两侧
pnpm --filter supplier-portal build --mode supplier
pnpm --filter supplier-portal build --mode outsourcing   # 降级：复用 supplier app 出外协产物

# 二期：物理拆分后各自独立
pnpm --filter outsourcing-portal build
```

约束：`PORTAL_MODE` 只用于「路由/菜单/品牌」分流；**权限与数据隔离仍由后端 token 的 `partner_type` 强制**，前端开关不得作为安全边界。

## 10. ADR-007（门户拆分，完整五要素）

- **背景**：四端法律主体、权限域、发版节奏、SLA 不同，但领域对象与 UI 骨架重合度 ≥ 70%。
- **选项**：A 单一 app 多角色（省事但数据/权限耦合、发版互相阻塞）；B 四套完全独立仓库（隔离彻底但三倍缺陷与口径漂移）；C Monorepo + 多 app + portal-core。
- **决策**：选 C。分应用保证隔离与独立发版，共享内核避免重复，`PORTAL_MODE` 提供降级加速。
- **后果**：Monorepo 需 Turborepo 治理依赖与缓存；portal-core 的 API 变更需全端回归；前端安全边界仍由后端强制。
- **回滚条件**：若 portal-core 频繁被某端「破坏性改动」拖累他人发版（月冲突 > 3 次），则将 portal-core 冻结版本 + 各端锁版本，或按端 fork 内核。
