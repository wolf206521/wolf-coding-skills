## 1. 总体架构分层

自上而下五层，层间只允许「上层依赖下层」，禁止反向依赖与跨层跳跃。

| 层 | 组成 | 关键选型 |
| --- | --- | --- |
| **前端层** | 5 个应用 + `portal-core` 共享内核（Monorepo） | React 18 + TS 5.5 + Vite 5 / Taro 4 |
| **网关层** | API 网关 | Spring Cloud Gateway / APISIX |
| **后端层** | `erp-server`（模块化单体）+ `ai-service`（独立进程） | Spring Boot 3.3 + Spring Modulith；FastAPI + LangGraph |
| **数据层** | 关系库 + 缓存 + 消息 + 检索 + 文件 + 向量 | PostgreSQL 16 / Redis 7.2 / RocketMQ 5 / ES 8 / MinIO |
| **基础设施层** | 编排、CI、制品、观测、备份 | Docker Compose → K8s / Argo CD / OTel / pgBackRest |

## 3. 模块化单体 vs 微服务（ADR-001，核心决策）

### 3.1 背景

P-ERP 首期只有「一家印刷厂 + 若干试点客户」的规模；团队尚无微服务运维经验；报价/订单/排产是强事务链（下单必须同时扣减纸张预留、生成工单、写对账单），跨服务分布式事务会显著抬升复杂度。但业务边界清晰（19 个模块），未来有多法人、多工厂、分库分表诉求。

### 3.2 选项

| 选项 | 说明 | 评估 |
| --- | --- | --- |
| A. 微服务起步 | 每个模块一个服务，独立部署/扩容 | 运维成本高、分布式事务难、首期产能被基础设施吞掉 |
| B. **模块化单体（Spring Modulith）** | 单进程、单库，但模块边界用代码强制校验 | 单点事务、部署简单、边界可验证、可平滑拆分 |
| C. 传统大泥球单体 | 无边界约束，包互相依赖 | 门槛低但技术债不可控 |

### 3.3 决策

**选 B。** 用 Spring Modulith 1.2 起步：模块内聚、模块间只经「应用事件 + 公开 API」通信，ArchUnit + Modulith 校验器在 CI 阻断跨模块内部包依赖。**拆分是"被指标逼出来"的结果，不是起点**。

### 3.4 后果

- ✅ 单库事务保证「订单→工单→库存预留」原子性；运维只需 1 个进程。
- ✅ `@Modulithic` 结构测试强制依赖方向，坏味道在编译期/CI 暴露。
- ⚠️ 单点故障面大、无法按模块独立扩容，模块级发布粒度粗；数据库单点，未来分库需按分片键改造。

### 3.5 回滚条件（拆分触发指标）

满足**任意 2 条**即启动某模块微服务化评估（见 `10-迭代进化与度量.md`）：

1. 某模块 CPU/内存占用持续 > 60%，且与主链路争抢资源；
2. 某模块发布频率 > 2 倍/周 且要求独立上线不锁全局；
3. 某表 > 5000 万行且读写热点导致锁等待；
4. 需要独立团队并行交付，模块间依赖通过事件已解耦。

拆分顺序（预排）：`ai`（已独立）→ `integration` → `aps` → `finance`。

## 4. 后端 Spring Modulith 模块清单与依赖规则

### 4.1 模块清单（19 个，与 `_conventions.md` 第 4 节一致）

| 模块 | 职责 | 领域聚合示例 |
| --- | --- | --- |
| `quotation` | 报价 | `Quotation` |
| `order` | 销售订单 | `SalesOrder` |
| `prepress` | 印前/文件预检 | `PrepressJob` |
| `craft` | 工艺/BOM | `CraftSheet` |
| `aps` | 排产 | `ProductionPlan` |
| `production` | 工单/MES | `WorkOrder` |
| `material` | 纸张物料/库存 | `PaperStock` |
| `supplier` | 供应商 | `Supplier` |
| `outsourcing` | 外协 | `OutsourcingOrder` |
| `quality` | 质量 | `QualityCheck` |
| `warehouse` | 仓储物流 | `Shipment` |
| `finance` | 财务/成本/对账 | `Statement`、`CostSheet` |
| `crm` | 客户 | `Customer` |
| `ai` | AI 能力网关（只读调用其余模块） | `AiJob` |
| `iam` | 认证授权 | `User`、`Role` |
| `tenant` | 多租户 | `Tenant` |
| `audit` | 审计（订阅事件，只写） | `AuditLog` |
| `integration` | 外部系统防腐 | `ExternalAdapter` |

### 4.2 依赖规则

1. `iam`、`tenant`、`audit` 为**横切基础模块**，只可被依赖，不得反向依赖业务模块。
2. 业务模块间**只允许依赖方向指向"更基础/更上游"**，禁止成环。
3. 模块间业务交互走 `ApplicationModuleListener` 事件（RocketMQ），**禁止直接调用对方内部 service**；跨模块只读查询经 `ai`/`audit` 网关/订阅模块或公开查询 API，禁止绕过。

### 4.3 依赖方向图（箭头 = 允许依赖）

```
        ┌─────────────────────────────────────────────────────────────┐
        │   finance  ◄── order, production, outsourcing, warehouse, crm │  (最下游/结算)
        └──────────────▲────────────────────────────────────────────────┘
                       │
   order ──► quotation ──► crm, material, craft
   production ──► order, craft, material, aps
   aps ──► order, craft, material, production(只读)
   outsourcing ──► production, supplier
   quality ──► production, order, outsourcing
   warehouse ──► production, material, order
   prepress ──► order, craft
   integration ──► order, production, finance
   ai ──► quotation, order, prepress, craft, aps   (只读网关)
   audit ──► (订阅全部业务事件，不反向依赖)
   ─────────────────────────────────────────────────
   iam / tenant（横切，被全部模块依赖，永不反向）
```

## 5. 事件驱动（RocketMQ 事务消息、幂等）

### 5.1 事件规范

- 事件命名 `<domain>.<aggregate>.<past-tense-verb>`，如 `order.sales-order.submitted`（与 `_conventions.md` 第 4 节一致）。
- Topic 命名：`perp-{module}-{aggregate}`；消费组 `perp-{module}-{consumer}`。
- 消息体携带 `traceId`、`tenant_id`、`partner_id`、`event_id`、`occurred_at`、`schema_version`。

### 5.2 事务消息（关键链路：订单提交）

`RocketMQ 事务消息` 保证本地事务与消息投递原子：

```
订单模块事务:
  1. beginTransaction → 写 sales_orders 状态=SUBMITTED
  2. 发送半消息 order.sales-order.submitted
  3. 本地事务提交 → commit 消息
  4. 消费方: production(建工单) / material(预留纸张) / finance(记账)
  5. 若 4 失败 → 回查订单状态，一致则重投，最终一致
```

```java
// 发送事务消息（订单模块）
TransactionMQProducer p = new TransactionMQProducer("perp-order");
p.setTransactionListener(new OrderTransactionListener()); // execute/checkLocalTransaction
p.sendMessageInTransaction(new Message("perp-order-sales-order", body), orderId);
```

### 5.3 幂等设计（消费端必须）

消费方以 `event_id` 为唯一键落库去重：

```sql
CREATE TABLE event_consumed (
  event_id   VARCHAR(64) PRIMARY KEY,   -- 事件唯一 id
  handler    VARCHAR(128) NOT NULL,     -- 消费方法标识
  consumed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

消费入口：先 `INSERT ... ON CONFLICT (event_id) DO NOTHING`，返回 0 行说明已消费则直接 ACK 跳过；返回 1 行再执行业务，业务失败回滚去重记录并 `RECONSUME_LATER`。

## 6. 缓存与一致性策略

### 6.1 缓存分层与用途（Redis 7.2）

| 用途 | Key 约定 | TTL | 一致性策略 |
| --- | --- | --- | --- |
| 会话/Token | `sess:{jti}` | access 15min / refresh 14d | 删除即失效 |
| 幂等锁 | `idem:{event_id}` | 24h | SET NX |
| 分布式锁 | `lock:{resource}:{id}` | ≤ 10s（Redisson 看门狗） | 释放即失效 |
| 热点字典 | `dict:{type}:{code}` | 1h | Cache-Aside + 事件失效 |
| 报价规则 | `quote:rule:{version}` | 长期（版本化） | 发布新版本整体替换 key |

### 6.2 Cache-Aside + 事件失效（ADR-005）

**读**：先查 Redis → miss 回源 PG → 回填（TTL）。
**写**：先写 PG → 发领域事件 → 消费方 `DEL dict:{...}`，而非先删缓存（避免双删竞态）。

回滚条件：出现缓存穿透/击穿热点时，引入布隆过滤器 + 空值缓存兜底；出现跨服务强一致需求时，升级为 CDC（Debezium）驱动缓存。

### 6.3 缓存穿透/击穿防护（一期就做）

```java
// 空值缓存 + 互斥重建（Redisson 锁），NULL 值缓存 60s 防穿透
String v = redis.get(key);
if (v == null && redis.setIfAbsent("lock:" + key, "1", 10, TimeUnit.SECONDS)) {
    v = db.load(key);
    redis.set(key, v == null ? "NULL" : v, 1, TimeUnit.HOURS);
    redis.del("lock:" + key);
} else if (v == null) { Thread.sleep(50); v = redis.get(key); }
```

## 7. 多租户与数据隔离三层防线

> 全文见 [`_conventions.md`](./_conventions.md) 第 5 节，此处给出落地要点与验收。

| 层 | 隔离键 | 实现 | 覆盖端 |
| --- | --- | --- | --- |
| ① 租户级 | `tenant_id` | 租户上下文注入 + 查询拦截器自动拼接 | 全部 |
| ② 合作方级 | `partner_id` + `partner_type` | MyBatis/JPA 拦截器 + PostgreSQL **RLS** 双保险 | 协同三端 |
| ③ 字段级 | DTO 裁剪 | 后端 Assembler 按角色裁剪字段，价格/成本/他人信息不进入响应 | 协同三端 |

RLS 落地（PostgreSQL 16）：

```sql
ALTER TABLE sales_orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY partner_isolation ON sales_orders
  USING (partner_id = current_setting('app.partner_id')::bigint
         AND partner_type = current_setting('app.partner_type'))
  WITH CHECK (partner_id = current_setting('app.partner_id')::bigint);

-- 连接后设置会话变量（由网关鉴权后注入）
SET app.tenant_id = '1'; SET app.partner_id = '1001'; SET app.partner_type = 'customer';
```

验收：以 `customer A` 的 token 请求 `GET /api/v1/orders?partner_id=<B>`，必须返回空集或 403；响应体中不得出现 `cost`、`unit_price`、`supplier_price` 字段。

### 8.2 扩展策略

- **水平扩展**：`erp-server` 无状态化（会话外置 Redis），网关后挂 N 副本，仅数据库单点；**分片预留**：表按 `tenant_id` 设计分区键，二期接入 ShardingSphere 5.5 按租户分库分表。
- **文件/检索分离**：MinIO 与 ES 独立扩缩容，PG 只存元数据；**DB 单点保护**：读写分离 + 连接池，核心表按 `created_at` 月分区。

## 9. 性能目标（P95 阈值）

与 `_conventions.md` 第 2.4 节一致，一期即按此压测：

| 场景 | 阈值 | 压测工具 | 门禁 |
| --- | --- | --- | --- |
| 普通查询（列表/详情/字典） | P95 < 500ms | k6 | 达标才可发生产 |
| 复杂报表/对账导出 | P95 < 2s | JMeter | 达标 |
| 订单提交（事务链路） | P95 < 1s | k6 | 达标 |
| 文件上传（150MB 分片） | P95 < 10s | k6 | 达标 |
| 大文件下载 | 吞吐 ≥ 500 MB/s | k6 | 达标 |
| 报价引擎单次试算 | P95 < 800ms | k6 | 达标 |
| 错误率 | < 0.1% | k6 | 达标 |
| 可用性（月度） | ≥ 99.9% | Prometheus | 达标 |

压测基线脚本（`tests/performance/k6/order-submit.js`）示例：

```js
import http from 'k6/http';

export const options = { thresholds: { http_req_duration: ['p(95)<1000'], http_req_failed: ['rate<0.001'] } };

  const h = { 'Content-Type': 'application/json', Authorization: `Bearer ${__ENV.TOKEN}` };
  const r = http.post('https://staging.perp.local/api/v1/orders',
    JSON.stringify({ customerId: 1001, product: '书刊-16开-胶装', quantity: 3000 }), { headers: h });
  check(r, { 'status 201': (x) => x.status === 201 });
  sleep(1);
}
```

## 10. 关键 ADR 汇总（至少 4 条，均 5 要素）

| 编号 | 决策 | 摘要 | 回滚条件 |
| --- | --- | --- | --- |
| ADR-001 | 模块化单体起步 | 见 §3，边界用 Modulith 强制 | 满足 §3.5 任意 2 条 |
| ADR-002 | 契约优先 API-First | 后端 OpenAPI 3.1 → 生成 TS/Java client | 前端大量手写类型即判定失败 |
| ADR-003 | AI 服务独立进程 | Python/LangGraph 解耦 Java 主干 | AI 调用成为主链路硬阻塞时合并评估 |
| ADR-004 | RocketMQ 事务消息 | 订单-库存-工单最终一致 + 幂等 | 事务消息回查成本超阈值则降级 Outbox |
| ADR-005 | Cache-Aside + 事件失效 | 见 §6.2 | 出现热点强一致需求升级 CDC |
| ADR-006 | 三层数据隔离 | tenant+partner+字段脱敏 | 出现跨租户查询审计不可行时增隔离 |

> ADR-004 的完整五要素已并入 §5（事务消息 + 幂等），ADR-006 已并入 §7（三层防线），此处不重复；每条的「背景/选项/决策/后果/回滚条件」在对应小节逐项核对。

## 11. 验收清单

- [ ] `erp-server` 通过 `@Modulithic` 结构测试，模块无环、无跨模块内部包依赖（§4.3）。
- [ ] ArchUnit 测试在 CI 生效，`iam`/`tenant` 不依赖任何业务模块。
- [ ] 订单提交走 RocketMQ 事务消息，消费端 `event_consumed` 幂等去重可用（§5.3）。
- [ ] `sales_orders` 开启 RLS，合作方 A 无法读到合作方 B 数据（§7）。
- [ ] 协同端响应体不含 `cost`/`unit_price`/`supplier_price` 字段（§7 验收）。
- [ ] k6 压测 P95：查询 < 500ms、订单提交 < 1s、报表 < 2s、错误率 < 0.1%（§9）。
- [ ] 容量估算表（§8.1）数值经试点工厂实际数据校准一次。
- [ ] 本文件 6 条 ADR 均有「背景/选项/决策/后果/回滚条件」五要素，且与 `_conventions.md` 一致。
