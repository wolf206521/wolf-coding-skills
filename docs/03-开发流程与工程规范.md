# 03 开发流程与工程规范

> 本文定义「需求 → 交付」闭环、代码规范、PR 门禁、DoD 与本地开发环境。
> 命名/目录/分支基线以 [`_conventions.md`](./_conventions.md) 为唯一事实源；总体架构见 [`01-架构设计.md`](./01-架构设计.md)；门户拆分见 [`02-多端与门户拆分.md`](./02-多端与门户拆分.md)。测试门禁见 `04-自动化测试策略.md`，分支与发布详见 `05-版本管理与分支策略.md`，CI/CD 见 `06-CICD与部署.md`。

## 1. 需求到交付的完整流程（一张流程图）

```
        ┌────────────────────────────────────────────────────────────────────────────┐
        │  需求/原型(外部项目)                                                          │
        └──────────────┬─────────────────────────────────────────────────────────────┘
                       ▼
              ① 澄清 (clarify)      wolf-project-kickoff：澄清式提问，产出验收标准(AC)
                       ▼
              ② 建模 (model)        领域词汇表 + 聚合/事件/状态机，产出 ADR 草案
                       ▼
              ③ 契约 (contract)     OpenAPI 3.1 + JSON Schema + Pact，产出可生成 client 的契约
                       ▼
              ④ TDD (red-green-refactor)  wolf-tdd-loop：先写失败测试 → 实现 → 重构
                       ▼
              ⑤ PR (review)        见 §5 PR 审查 Checklist + 全部门禁
                       ▼
              ⑥ 门禁 (gate)        lint → test → build → sbom/scan → 契约校验（全绿才可合入）
                       ▼
              ⑦ 灰度 (canary)      staging → 金丝雀/分批 → 回滚预案
                       ▼
              ⑧ 观测 (observe)     OpenTelemetry + 指标/日志/审计 + 业务度量
                       ▼
              ⑨ 迭代 (evolve)      双周回顾 → ADR 演进 → 技术债看板
                       │
                       └────────── 度量与反馈回灌 ① 澄清 ──────────┘
```

**每个阶段的出口门禁**：

| 阶段 | 入口 | 出口（不可跳过） |
| --- | --- | --- |
| ① 澄清 | 需求/原型 | 每条需求有可测 AC，模糊点已提问闭环 |
| ② 建模 | AC | 聚合/事件名与 `_conventions.md` 命名一致 |
| ③ 契约 | 模型 | OpenAPI 可生成 client，无手写类型 |
| ④ TDD | 契约 | 先红后绿，核心域覆盖达标 |
| ⑤ PR | 代码 | 走完 §5 清单，无未解决评论 |
| ⑥ 门禁 | PR | CI 全绿 + 契约漂移=阻塞 |
| ⑦ 灰度 | 制品 | 灰度指标正常，有回滚预案 |
| ⑧ 观测 | 上线 | traceId/审计/指标就绪 |
| ⑨ 迭代 | 度量 | 回顾产出 ADR/技术债条目 |

## 2. 需求未就绪前提下的并行策略

**前提**（来自 `00-master-plan.md` §1.1）：需求文档与原型在另一个项目维护、尚未交付。**不空转**，分两条线并行：

### 2.1 可立即启动的「工程能力线」

1. 脚手架成型：`templates/` 生成 Monorepo（5 app + portal-core + 后端 + AI 服务）一次通过。
2. CI 全绿：lint/test/build/scan 流水线跑通（见 `06-CICD与部署.md`）。
3. 契约骨架：用**行业样例数据 + 假需求**产出第一版 OpenAPI（报价/订单/对账三条链路）。
4. 观测与部署：Compose 单机跑通 + OTel 采集 + 灰度脚本就绪。

### 2.2 需求就绪后的「增量接入线」

需求文档到位后按 `wolf-project-kickoff` 增量接入：把每个假需求替换为真 AC，**只改契约与实现，不动流水线**。样例数据（`tests/fixtures/` 印刷纸张/工艺/订单样例）作为回归基线保留。

### 2.3 边界约定

- 假需求代码一律打 `chore(seed):` 或 `feat(seed):` 标签，避免与真实需求混淆。
- 假需求**不进入生产门禁的"业务验收"**，只用于打通工程链路。

## 3. 代码规范（Java / TS 统一风格）

### 3.1 目录规范

- 后端 DDD 四层：`interfaces / application / domain / infrastructure`（包根 `com.wolf.perp`，见 `_conventions.md` 第 4 节目录树）。
- 前端 app：`src/{pages,components,features,hooks,api,store}`；共享内核在 `packages/portal-core`。

### 3.2 命名规范（与 `_conventions.md` 第 4 节一致）

| 对象 | 规范 | 示例 |
| --- | --- | --- |
| 数据库表 | `snake_case` 复数 | `sales_orders` |
| 字段 | `snake_case`；FK `<table_singular>_id`；时间 `<verb>_at`；布尔 `is_/has_` | `customer_id`, `submitted_at`, `is_paid` |
| Java 类/方法/常量 | `UpperCamel` / `lowerCamel` / `UPPER_SNAKE` | `SalesOrder`, `submit()`, `MAX_OPEN_ORDERS` |
| TS 组件/hook/工具 | `PascalCase.tsx` / `useXxx.ts` / `kebab-case.ts` | `OrderDetail.tsx`, `useOrders.ts`, `format-price.ts` |
| API | `/api/v1/{domain}/{resource}`，资源复数，动作用子资源 | `POST /api/v1/orders/{id}/submit` |
| 事件 | `<domain>.<aggregate>.<past-tense-verb>` | `order.sales-order.submitted` |
| Git 分支 | `feat/PE-123-quotation-engine` | 关联需求号 |

### 3.3 格式化与静态检查（强制，写入 pre-commit + CI）

```yaml
# .pre-commit-config.yaml
repos:
  - repo: local
    hooks:
      - id: java-format
        name: spotless
        entry: ./gradlew spotlessApply
        language: system
        pass_filenames: false
      - id: ts-lint
        name: eslint+prettier
        entry: pnpm lint:fix
        language: system
        pass_filenames: false
```

```bash
# 后端（Gradle）
./gradlew spotlessCheck checkstyleMain        # 风格门禁
./gradlew test                                # 单测
# 前端（pnpm + Turborepo）
pnpm lint && pnpm typecheck && pnpm test      # 全仓门禁
```

## 4. 分支与提交规范（概述，指向 05）

> 完整规则见 `05-版本管理与分支策略.md`。此处仅列工程约束，避免重复。

- **Trunk-based + 短分支**：`main` 永远可发布；`feat/*` `fix/*` `hotfix/*` ≤ 3 天；`release/x.y` 仅 LTS。
- **Conventional Commits**：`feat|fix|docs|refactor|perf|test|build|ci|chore|revert(scope): subject`。
- **禁止直接 push `main`**；PR 必须过全部门禁；SemVer 按端独立，Changesets 生成 `CHANGELOG.md`。

```bash
# 标准工作流（含需求号）
git checkout -b feat/PE-123-quotation-engine
# ... 开发 ...
git commit -m "feat(quotation): add cost composition engine for PE-123"
gh pr create --title "feat(quotation): quotation engine" --body "Closes PE-123"
```

## 5. PR 审查 Checklist

> 审查者逐条勾选；任一条未过即退回，禁止"口头通过"。

**正确性**

- [ ] 变更符合需求 AC，且 AC 已转成自动化测试（`tests/e2e` 或单测）。
- [ ] 契约变更同步更新 OpenAPI，重新生成 client，无手写类型漂移。
- [ ] 事件命名/消息体 schema 符合 `<domain>.<aggregate>.<verb>` 且含 `event_id`（幂等键）。

**架构与依赖**

- [ ] 未引入跨模块内部包依赖（ArchUnit/Modulith 校验通过）。
- [ ] `iam`/`tenant`/`audit` 未反向依赖业务模块（见 `01-架构设计.md` §4.3）。
- [ ] 新增外部依赖有选型理由，SBOM 扫描无新增高危。

**安全与数据**

- [ ] 协同端响应 DTO 无 `cost`/`unit_price`/`supplier_price` 泄露（见 `02-多端与门户拆分.md` §4）。
- [ ] 查询带 `tenant_id`/`partner_id` 过滤，写操作有审计。
- [ ] 密钥/凭证未入库（Vault/SOPS），SQL 无注入（参数化）。

**质量与可观测**

- [ ] 单测通过，核心域覆盖 ≥ 85%；变异测试（核心域）杀死率 ≥ 60%。
- [ ] 新增/变更路径有 traceId 贯穿，日志结构化 JSON。
- [ ] 性能敏感路径附 k6/JMeter 结果，P95 达阈值（见 `01-架构设计.md` §9）。

**可回滚**

- [ ] 数据库迁移为向前兼容（Expand/Contract），回滚=切回旧镜像。
- [ ] 变更可独立灰度，有回滚预案与观测指标。

## 6. Definition of Done（DoD 清单）

一条需求「完成」必须**全部满足**：

- [ ] 需求 AC 全部实现，且有自动化测试覆盖（E2E/单测/契约）。
- [ ] 代码通过 pre-commit + CI 全部门禁（lint/test/build/scan）。
- [ ] OpenAPI 契约已更新，client 重新生成，无手写类型。
- [ ] 数据库迁移脚本随 PR 合入，且向前兼容。
- [ ] 核心域单测覆盖 ≥ 85%，变异杀死率 ≥ 60%，契约漂移=0。
- [ ] P0 场景 E2E 全绿；性能敏感路径 P95 达标。
- [ ] 安全门禁：高危漏洞 = 0，密钥未入库，数据脱敏生效。
- [ ] 文档/ADR/`CHANGELOG` 同步更新，交叉链接无死链。
- [ ] 已在 staging 灰度验证，有观测指标与回滚预案。
- [ ] 发布说明（commit 自动汇总）与 `<app>@<version>` 标签一致。

## 7. 本地开发环境搭建（一键脚本）

### 7.1 依赖环境（版本与 `_conventions.md` 一致）

| 工具 | 版本基线 | 说明 |
| --- | --- | --- |
| JDK | 21 LTS | 虚拟线程 |
| Node + pnpm | 20 + pnpm 9 | Monorepo 编排 Turborepo 2 |
| Docker | 24+ | PG/Redis/RocketMQ/MinIO 本地编排 |
| Python | 3.12 | `ai-service` 独立 venv |

### 7.2 一键启动（`scripts/dev-up.ps1`）

```powershell
# scripts/dev-up.ps1  （PowerShell，Windows）
$ErrorActionPreference = 'Stop'
# 1) 启动中间件（PostgreSQL/Redis/RocketMQ/MinIO/ES）
docker compose -f platform/compose/docker-compose.dev.yml up -d
# 2) 初始化数据库（Flyway 迁移 + 种子数据）
./gradlew :services:erp-server:flywayMigrate
./gradlew :services:erp-server:bootRun -Pprofiles=dev
# 3) 安装前端依赖 + 生成 API client + 启动门户
pnpm install
pnpm --filter api-client generate        # 由 OpenAPI 生成 TS client
pnpm dev                                 # Turborepo 并行起 5 个 app
# 4) AI 服务
cd services/ai-service; python -m venv .venv; .\.venv\Scripts\Activate.ps1; pip install -r requirements.txt; uvicorn app.main:app --reload --port 8000
```

Linux/macOS 等价脚本 `scripts/dev-up.sh`。本地访问（见 `02-多端与门户拆分.md` §9.2 域名）：

```bash
http://erp.local:5173        # ERP 后台
http://customer.local:5174   # 客户侧
http://supplier.local:5175   # 供应商侧
http://outsource.local:5176  # 外协侧
http://api.local:8080        # 后端网关
```

### 7.3 环境变量（`.env.dev`，密钥禁止入库，用 `.env.example` 提交）


## 8. Mock 与联调策略

### 8.1 契约优先下的 Mock 分层

| 层 | 工具 | 用途 |
| --- | --- | --- |
| 后端单元/集成 | Mockito + Testcontainers | 真实 PG/Redis/RocketMQ，不 mock 中间件 |
| 前端开发 | MSW（Mock Service Worker） | 以 OpenAPI schema 生成 mock，前端先跑通 UI |
| 联调 | WireMock / Prism | 用契约文件生成可交互 mock server |
| 契约测试 | Pact / Spring Cloud Contract | 前后端契约漂移=阻塞 |

### 8.2 前端 mock（MSW，由契约自动生成）

```ts
// apps/customer-portal/src/mocks/handlers.ts
import { http, HttpResponse } from 'msw';
import { getOrderHandler } from '@perp/api-client/mock'; // 由 OpenAPI 生成
export const handlers = [getOrderHandler({ status: 'SUBMITTED', quantity: 3000 })];
```

### 8.3 联调约定

1. **先契约后联调**：前端只认 `api-client` 生成的类型；后端只认 OpenAPI 校验（`springdoc` 校验请求/响应）。
2. **traceId 贯穿**：联调报错必须带 `traceId`，后端据此查 Loki 日志，禁止"截图问 bug"。
3. **假需求阶段**：用 `tests/fixtures/` 样例数据联调；真实需求到位后替换为真数据，不动 pipeline。
4. **AI 联调**：`ai-service` 用 `OPENAI_BASE_URL` 指向 One-API 网关，`curl http://localhost:8000/v1/quote` 冒烟后接入前端。
